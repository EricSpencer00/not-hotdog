How Not Hotdog works

demo  ·  source  ·  ericspencer.us

A 136,417-parameter convolutional network runs in your browser with no library behind it. This is how it was trained, how it was reduced to 8-bit integers, and how the convolutions are written in JavaScript that never touches a float.

1. The constraint

One rule set every decision: the page is an HTML file and one script, and after it loads it never talks to the network again. No TensorFlow.js, no ONNX Runtime, no WebAssembly, no npm. Your photograph is read from a canvas, resized, classified, and forgotten.

Running a neural network in a browser is not hard. There are three good libraries for it. What is interesting is running one with nothing: every operation has to exist as code somebody wrote, in integers, and the result has to be proved rather than asserted. A convolution bug does not crash. It makes the model slightly worse in a way nobody would ever notice.

2. What ships

96×96×3 input, a MobileNet-style depthwise-separable stack, ReLU only.

14.0M multiply-accumulates per forward pass, 133 KB of int8 weights, about 26 ms per image in Node on an M1 Max.

The architecture is chosen by what has to be written by hand later. Hard-swish, squeeze-excite, residual addition and concatenation are one line each in PyTorch and a new kernel each in JavaScript. So the network uses four operations and nothing else: a dense 3×3 convolution in the stem, then a depthwise 3×3 and a pointwise 1×1 in every block, with a ReLU after each. The head is a global average pool and one fully connected output.

3. Training

Positives are the binding constraint

The dataset holds roughly 1,800 hot dog photographs against 12,000 photographs of other food and 8,000 photographs of unrelated objects. The non-food negatives are there so the model learns is this a hot dog rather than is this a photo of food; without them every negative is a plated dish.

Shown that ratio directly, a 136K-parameter network learns to say no. A class-balanced sampler fixes the learning problem and creates a calibration one, which is dealt with at the end of this section.

A teacher that never ships

An ImageNet-pretrained EfficientNet-B0 is fine-tuned at 224px as the teacher. It has 5.3M parameters and reaches F1 0.837 at 97.6% accuracy on validation. Its only job is to produce soft targets, so it has a hard gate: below 96% validation accuracy the data pipeline is the thing to fix, not the recipe.

Distillation

The student trains for 30 epochs against the teacher's soft probability at temperature T=4. The distillation term is binary cross-entropy of the student logit against sigmoid(z_teacher / T), scaled by T² so the gradient does not collapse as the temperature rises. It carries a weight of α=0.7; the remaining 0.3 is ordinary cross-entropy against the hard label.

For a student 39× smaller this is most of the point. The hard label says "hot dog". The soft target says "0.83 hot dog", and that gap carries what the teacher knows about how hot-dog-like this particular photograph is.

One augmented crop feeds both networks: the teacher sees it at 224 with ImageNet normalization, the student sees the same crop at 96 scaled to [0,1]. If the two saw different augmentations, the soft label would describe an image the student never sees.

Calibration, then QAT

Activation ranges are observed in a separate pass with the weights frozen. You cannot fake-quantize an activation before you know its range, and you cannot know its range without running data through the trained network. Doing it as its own pass keeps the ranges honest: if the weights were still moving, the running average would track a distribution that no longer exists by the time training ends.

Then 8 more epochs of quantization-aware training at a tenth of the learning rate, with fake quantization in the graph and BatchNorm folded into the convolution.

Folding during QAT rather than at export matters. The fold rescales each output channel by γ/√(σ²+ε), which changes every per-channel maximum and therefore every weight scale. Train against unfolded weights and ship folded ones, and the weights that were trained are not the weights that run. BatchNorm statistics are frozen during this phase for the same reason: the fold reads the running mean and variance, so those have to stop moving or the folded weights drift under the quantizer.

Moving the threshold instead of retraining

Balanced sampling leaves the model with an implied prior of 50/50. The world it is deployed into is about 11:1 the other way, so thresholding the logit at zero fires far too eagerly.

The fix is calibration, not retraining. Every distinct int32 logit on the validation set is swept, and the one that maximises F1 is folded into the head bias at export. The shipped model's decision is then plainly accumulator > 0, and the browser carries no knowledge of the imbalance at all. The threshold is chosen on validation and reported on test, which is the only ordering that keeps the test number honest.

4. Eight bits

TensorScheme
weightsint8, per-output-channel symmetric, zero-point 0
activationsuint8, per-tensor symmetric, zero-point 0
biasint32 at scale s_w[c] · s_in
accumulateint32
requantizeRoundingDivideByPOT(SRDHM(acc, m0[c]), shift[c])

Zero-point 0 is the whole trick

Every activation in this network is the output of a ReLU, so it is never negative. Asymmetric quantization only buys range when values go negative, so activations are quantized as unsigned symmetric with zero-point 0. It costs nothing and it deletes two problems.

The zero-point correction term disappears from every accumulator: a convolution becomes a plain sum of products. And SAME padding becomes genuinely zero, rather than "the quantized value that represents zero", so a kernel can skip an out-of-bounds tap and be exactly right instead of approximately right.

The input scale is exactly 1/255

The student is trained on pixel/255, so its input quantizer lands on scale 1/255 with zero-point 0. The quantized input tensor is then bit-identical to the raw RGB bytes off the canvas, and preprocessing is a byte copy. The export step asserts this rather than hoping for it.

Requantization

Each layer's real multiplier is M = (s_w[c] · s_in) / s_out, one value per output channel. Export checks that M < 1 — the kernels only implement right shifts — and decomposes it into an int32 m0 ∈ [2³⁰, 2³¹) and a shift. These are gemmlowp's semantics exactly, which is deliberate: gemmlowp's rounding rules are precisely specified, so there is an existing definition to be correct against rather than a house convention.

5. The kernels

Four kernels, plus an integer pool and a dot product. That is the entire numerical part of the program.

KernelRole
conv3x3dense 3×3, SAME pad — the stem only
dwconv3x3depthwise 3×3, SAME pad — 7 call sites
pwconv1x1pointwise, a GEMM over channels — about 80% of the MACs
requantizeint32 → uint8, fused into the three above

The layout is NHWC everywhere. That makes the pointwise convolution a contiguous dot product along the channel axis — the inner loop walks the activation and the weight linearly — and it makes the activation taps behind the demo's "show internals" button a strided read instead of a transpose.

Accumulating in doubles, on purpose

Products are int8 × uint8, so no product exceeds 127 × 255 = 32,385. The longest accumulation is 3 × 3 × 256 = 2,304 terms, so the accumulator stays under 7.5×10⁷. That is far inside 2⁵³, where a double holds an integer exactly. The inner loops therefore use plain * and + and coerce to int32 once at the end. The arithmetic is exact and the loop stays fast.

The multiply that does not fit

Requantizing an int32 accumulator needs the high 32 bits of a signed 64-bit product. This is the one function the whole port rests on, and JavaScript cannot express it directly. A Number is a double with a 53-bit mantissa, so a * b for two int32 operands silently loses the low bits. BigInt is exact and far too slow to call once per output element.

The way out is to never form the 64-bit product. Split each operand into a signed high half and an unsigned low half:

const aHi = a >> 16;        // signed,   |aHi| <= 2^15
const aLo = a & 0xffff;     // unsigned, < 2^16
// a === aHi * 2^16 + aLo, exactly, for any two's complement int32

Then with A = aHi*bHi, B = aHi*bLo + aLo*bHi and C = aLo*bLo:

a*b = A*2^32 + B*2^16 + C

|A| <= 2^30, |B| < 2^32 and C < 2^32, so each one is an exact double. The useful part is that T = B*2^16 + C + nudge stays below 2^49 and is therefore also exact. Since a*b + nudge = (2A)*2^31 + T, the quotient by 2^31 falls out of a floor-divide of T alone. No 64-bit value is ever materialised.

It is verified against the Python reference over 1,000,000 random pairs plus every boundary combination — INT32_MIN, INT32_MAX, powers of two, the values where the high/low split carries. A million multiplies take about 50 ms, which is why this is a plain function call in the inner loop and not a BigInt.

The resize is hand-written too

The obvious way to get a 96×96 image is drawImage. Its resampling filter is not specified precisely and differs between Safari, Chrome and Firefox, so the same photograph would produce different bytes in different browsers and bit-exactness would hold in one of them only.

So the preprocessing is a centre crop to the largest square, then an area average over integer pixel ranges with round-half-up. That has exactly one possible answer, and reference/preprocess.py is the same arithmetic on the same integers.

Buffers and the worker

Every buffer is allocated once and reused. Camera mode runs 15 to 30 times a second, and allocating about 400 KB of typed arrays per frame would hand the garbage collector a steady job and put a visible stutter in the verdict. Two scratch buffers alternate as input and output between layers, each sized to the largest activation in the network. The whole engine runs in a Web Worker: the main thread posts a frame and receives a logit, so the interface never blocks.

6. Proving it

The same integer program exists twice: once in JavaScript, once in NumPy. They must produce identical int32 logits on every validation image. Not close. Identical.

TestWhat it establishes
fixedpoint1,000,000 random pairs and every boundary combination, exact
kernelseach kernel against NumPy: stride-2 on odd inputs, SAME-pad edges, int8 saturation
parityJS logit ≡ Python logit on every validation image

Both engines read the same exported bytes. One export step writes reference/model_int8.npz and dist/model.js from one checkpoint. If each loaded weights independently, a parity failure would be ambiguous between "the kernels disagree" and "the loaders disagree", and only the first is interesting.

Two more properties are tested because they are easy to break by accident. The activation taps are observational, so opening the internals panel cannot change the verdict. And repeated inference is stateless, so the reused buffers cannot leak the previous frame into the current one.

All of it runs in CI on every push, with numpy and node and no dataset, since the 133 KB exported model is committed.

7. What it gets wrong

Everything below is measured on the int8 model — the one that ships — with the browser's exact preprocessing, not on the float checkpoint.

Read F1, not accuracy. About 92.6% of the test split is negative, so a model that says "not a hot dog" to everything already scores 92.6%. The accuracy column is there because people expect it, not because it means much.

Adversarial accuracy, 81.3%, is below the majority baseline of 90.7%. That is not a rounding artefact. On this set the model is worse than a rock with "not a hot dog" written on it.

The per-class split says why, and it is more interesting than the aggregate. The model rejects things that are nearly hot dogs: it gets 119/136 of the held-out negatives, never once mistakes a dachshund for food, and correctly refuses 8 of 10 corn dogs. What it fails is hard positives, 3/14, driven by chili dogs — hot dogs buried under chili, which look nothing like the canonical article.

So the model has learned a narrow, prototypical hot dog, and it is conservative about anything outside that. Given 1,800 positives and 136K parameters, that is the result you would predict. It is worth stating plainly rather than reporting the flattering test number and moving on.

The teacher-to-student gap is the honest headline of the training pipeline: a 136K-parameter network does not match a 5.3M-parameter one, and distillation narrows the gap rather than closing it. What quantization costs on top of that is too small to measure, which is the part QAT was for.
